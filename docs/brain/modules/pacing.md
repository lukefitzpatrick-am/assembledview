# Module: Pacing & Delivery

Tracks actual delivery (Snowflake facts) against plan (Xano media plans) at line-item + burst grain, for live campaigns, "as of" a Melbourne date. Four philosophies coexist: **spend pacing** (search/social/programmatic, including modelled spend when `derive_spend_from_plan`), **estimated CM360 direct digital** (`estimateDirectDigitalSpend`, labelled from `spendMode`; a fee-inclusive budget with no media amount uses net media from that version's `mba_fee_snapshots` row), **verification counts** on the ad-serving DTO (`serving | no-data`, no `computePacing`), **fixed-cost** (direct — pre-computed in warehouse; reported replaces an estimate).

## Key files

- `lib/snowflake/pgLineItemSnapshotMap.ts` — Postgres snapshot row. `ASSUME_SPEND` is `assumeSpendForSnapshotLine` from `lib/spend/assumeSpendRule.ts` (offline families, or digital with `no_adserving` and no active `delivery_source_map` row). `BURSTS_JSON` bursts carry `assumedDailyCents`. The flag does not see Snowflake facts. `SP_REFRESH_FIXED_COST_REPORTED_DAILY` writes fixed-cost rows. `SP_REFRESH_ASSUMED_SPEND_DAILY` writes assumed cents (`REPORTED_SPEND` = cents / 100, `CAP_APPLIED` `assumed_spend`) and deletes those rows when the flag drops or a pacing fact row exists. A filtered call of the inner procedure delegates that one line to the set-based procedure.
- `lib/spend/assumeSpendRule.ts` — client-safe `assumeSpendForSnapshotLine` and `isAssumedSpendLine`. The snapshot map calls the first and still does not read Snowflake facts. App pacing calls the second: the snapshot rule, and no loaded row with impressions, clicks, or spend above 0 through the as-of date. Sources are the pacing, social, search, CM360, partner-file, and programmatic rows that surface already loaded. The lookup is the in-memory `delivery_source_map` seed. No per-line Snowflake query.
- `lib/spend/assumedSpend.ts` — even daily cents for a no-source line (`assumedDailyCents`). The window is the burst's own dates, or its panel flights when the line has them. The amount is `computeBurstAmounts` `deliveryMediaAmount` in cents. Bonus and `package_inclusions` return nothing. Client-pays uses delivery media. The remainder is on the last day only after the window has ended. Days after the as-of date are 0. Half-up is `toCents`. Label Assumed spend, `spendMode` `assumed`, `CAP_APPLIED` `assumed_spend`. Portfolio rows, pacing detail, and the client dashboard use that mode. One pacing channel per family, line ids kept. Dollars count in spend to date and pace. Expected to date for those lines is the same burst sum, so the pace is 100% On track. That sum replaces their share of the delivery-schedule slice in `channelExpectedToDate` and `resolveCampaignExpectedSpendToDate`. When Snowflake has no positive `assumed_spend` row, delivered is the app sum too, but only when `isAssumedSpendLine` is still true. A line with delivery rows is not assumed: CM360 stays on the estimate and the Estimated label, and its schedule slice stays in expected. A line already on search, social, programmatic, or ad-serving is skipped. Programmatic `fixed_cost` stays on the reported path. The dashboard section is Assumed spend for the six offline families, and for a direct-digital or BVOD line only when that line has no delivery rows. The report deck and AVA read it. The deck channel is Assumed spend. AVA names the dollars and keeps them out of CPM, CPC, and CTR.
- `lib/pacing/maths/index.ts` — pacing arithmetic + 7-state `PacingStatus` ladder (order mirrors Snowflake `V_LINE_ITEM_PACING` — DO NOT REORDER). Band edges are `PACING_STATUS_THRESHOLDS` in `status.ts` (90 / 110 / 115 percent of expected). Melbourne date helpers live here too.
- `lib/pacing/campaigns/fetchSearchPacingCampaignRows.ts` — search composer AND the shared master/version crawl (`fetchAllMasters`, `fetchCurrentVersionRowsForMasters`, Postgres via `readPacing`). `fetchCurrentVersionRowsForMasters` passes its MBA set into `readPacingVersions`. Search **line items** resolve live masters then `readPlanVersionsForMbas` (no `legacy_schedules`) and published `line_items`. `campaign_kpi` is `lib/xano/campaignKpi` → `readKpi`.
- `lib/pacing/plans/resolveLivePlanLineItems.ts` — programmatic / social / ad-serving live lines. ## Snowflake tables

## Partner file ingest

`GET|POST /api/cron/partner-ingest` (Vercel `30 22 * * *` only, `maxDuration` 300). Sequence: Graph token (`lib/partner-ingest/graphToken.ts`, `PARTNER_INGEST_*`, 60s skew, scope `https://graph.microsoft.com/.default`) → every inbox message with attachments (`@odata.nextLink` followed) → two-factor `PARTNER_SOURCE_MAP` → per source, newest message first (files are cumulative): only the newest is parsed and loaded; once it lands, older pending mail for that source is logged `superseded` (no parse, no load) and moved to the Superseded folder; if the newest fails, the next newest is tried → SHA-256 skip if already `loaded` → INSERT raw lines → `parserForSource(SOURCE_SLUG)` (`lib/partner-ingest/parsers/index.ts`; `channel-factory` → Channel Factory, `vistar` → Vistar exchange; an unmapped slug files the mail as `unrecognised`) → parse (header by Day+Impressions in first 20 rows; map by column name) → T1+T5+T6 gate the load; T4 is a warning on `ERROR_TEXT` and the run summary and does not block (T4/T5 `n/a` when the source has no video columns; T5 scoped to `VIDEO_VIEWS > 0`; T6 reconciles the supplier totals row to ≤0.5% on impressions and revenue; values in the run summary; C-123) → DELETE+INSERT per `LOAD_MODE` on a held JWT session → move mail (never delete) → staleness sweep into `staleSources[]`. Uncoded media buys load. Parser fixtures: `channel-factory-2026-09-14.xlsx` (the 14 Sep Datorama attachment) and `vistar-exchange-sample.csv` (200 rows of the 15 Sep exchange report with its 6-line preamble and totals row). Date cells may be Date, Excel serial, `YYYY-MM-DD` or `d-MMM-yy`.

Channel Factory drops its first-cell `total*` row; Vistar's totals row has a blank `Day` and is kept in `PARTNER_FILE_LINES` for T6 only. Vistar carries the exchange columns (`AMOUNT_SPENT` = Revenue, the client cost; `PLAYS` = Spots; `VENUE_TYPE`, `METRO_AREA`, `STATE`, `PARTNER_CAMPAIGN_ID`, `PARTNER_CREATIVE_ID`) which Channel Factory binds NULL. Vistar impressions are fractional in the file and rounded once at the INSERT. Its plan code comes from `Contract Number` via `extractPlanCode`, whose regex covers `PV` (video) and `PO` (out-of-home) codes.

## Fixed-cost money path (partner file)

Channel Factory does not report platform cost. `MART.VW_PACING_PARTNER_FILE` filters `RAW.PARTNER_DELIVERY_DAILY` (`SOURCE = 'Channel Factory'`, coded `AV_LINE_ITEM_ID` only), sets `AMOUNT_SPENT = 0`, and MERGEs into `PACING_FACT` via `TSK_REFRESH_PACING_FACT`. `TSK_REFRESH_FIXED_COST_REPORTED` then calls `SP_REFRESH_FIXED_COST_NIGHTLY` (3-day window, then backfill partner-file / direct-digital lines so late files do not lock zeros, then `SP_REFRESH_ASSUMED_SPEND_DAILY('changed')`). The inner `SP_REFRESH_FIXED_COST_REPORTED_DAILY` writes `FIXED_COST_REPORTED_DAILY_FACT.REPORTED_SPEND` — the figure the Direct reader overlays onto `fixedCostMedia` programmatic and Direct Booked Digital lines. `factTableForSource` routes `prog_*` and `media_plan_digi_{bvod,video,display,audio}` to `PACING_FACT`. CALL with lowercase ids. CPV in the proc still reads `VIDEO_3S_VIEWS`, so the view dual-writes `SUM(COMPLETED_VIEWS)` there until the proc reads `COMPLETED_VIEWS` directly. Completions and video views stay distinct (C-123).

Vistar exchange reports use the same mailbox cron. Path: Vistar email → `/api/cron/partner-ingest` (`parserForSource('vistar')`, `LOAD_MODE` `range_replace`) → `RAW.PARTNER_DELIVERY_DAILY` (`SOURCE = 'Vistar'`) → `MART.VW_PACING_PARTNER_OOH` (`RAW.PARTNER_LINE_MAP` resolves the line at read time — aggregated to one row per campaign before the join, C-126 — or a `{mba}P[VO]{n}` code on the file; unmapped rows stay in RAW) → `PACING_FACT` channel `'Programmatic - OOH'` via `TSK_REFRESH_PACING_FACT` (no 14-day filter; the report restates YTD) → campaign delivery Programmatic OOH section and `/pacing/programmatic`. Broadsign buys arrive inside the Vistar exchange report (no Broadsign mailbox). `RESULTS` on this channel is plays (`SUM(PLAYS)`, C-128) and is a KPI on campaign delivery, not the CPM deliverable — that is `IMPRESSIONS` (same unit as plan `calculatedValue`). CPM lines carry Vistar Revenue as `AMOUNT_SPENT`; `fixedCostMedia` lines take overlay spend from `SP_REFRESH_FIXED_COST_REPORTED_DAILY` → `REPORTED_SPEND`.

## Gotchas (verified)

- **Caching:** 4h TTL; only invalidation = orphan assign. Key includes `asOfDate` → cold full-crawl each Melbourne midnight. Overview deliberately passes the auth scope (not live-client scope) to hit the tabs' warm cache entries. Three parallel cache mechanisms (unstable_cache, module Map in `pacingCache.ts`, private Map in avaSnowflake) — only the first is tag-invalidatable. `getDeliveredTotalsFor*` bypass the cache entirely.
- **Fuzzy channel matching** in SQL — a warehouse channel rename yields zero rows silently. Social / programmatic / ad-serving Snowflake fact fetches **rethrow** on failure (M7 — outage must not look like "no campaigns"); route/UI boundaries map to ViewState error / HTTP 5xx.
- **Two Snowflake read stacks** with different clamps/semantics: pacing pages vs `/api/pacing/bulk` + campaign dashboard — same MBA can show different numbers. Bulk `nonSocialSql` WHERE admits programmatic display, video, **OOH**, and ad serving (`bulkNonSocialChannelWhere`); CASE / `ALLOWED_CHANNELS` already map `programmatic-ooh` but the WHERE used to drop `Programmatic - OOH` rows.
- **Security:** the 4 per-channel POST routes (prog display/video, social meta/tiktok) use the same `checkClientMbaAccess` + line-item MBA-prefix gate as `/api/pacing/bulk` (SEC-7 FIXED). `POST /api/pacing/search` derives each line item's MBA via `parseMbaNumberFromLineItemId` then `checkClientMbaAccess` — never trusts a client id→MBA map (SEC-11).
- Direct re-implements the warehouse proc's 3-day rolling lock window in TS (`isOutsideRollingWindow`) — drift risk.
- Duplication: `lineItemStatusFromPacing` ×3 thin wrappers over `pacingStatus()`; KPI-target block ×3; `resolveLive*LineItems` ×3; page clients ×5; `count*OverviewStatus` ×5. Aggregators social vs programmatic have drifted (prog computes cpm, social doesn't; social passes 0 conversions/revenue → ROAS/CPA structurally absent).
- Sticky-column freeze patterns diverge sharply across the five channel tables (search densest; ad-serving/direct thinnest) — unify in a later commit; height maths already shared via `pacingTableScroll.ts`.
- `docs/archive/PERF-DISCOVERY-*` docs are stale on caching — trust `pacingRowsCache.ts`, not them.
- Genuine differences — don't unify blindly: direct's grouped shape + `includeHistorical`; ad-serving DTOs stay verification counts while direct digital dollars come from `estimateDirectDigitalSpend`; social's absent revenue.
- Direct channel tab (`DirectCampaignsClient`) maps load/filter outcomes through `ViewState` / `ViewStateBoundary` (error ≠ empty; filter-zero → Clear filters via `resetToDefaults`).
- Client filter fail-closed: when `client_ids` are selected but `clientIdToName` is empty, `applyPacingRowFilters` / `filterDirectCampaignGroups` return zero rows and channel clients show `PacingClientFilterUnavailable` (never silently widen). Client-name Set membership uses `normalizeSearchText` only (exact after normalise); free-text `search` uses `matchText` — scope semantics unchanged.
